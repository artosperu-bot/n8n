## 3. Raíces prioritarias por corregir

### R1 — Candidate Authority / Recommendation Engine — CRITICAL
Todo nombre de producto propuesto al cliente debe provenir de SQL catálogo autorizado. El writer no puede crear alternativas.

El recomendador debe hacer:
`necesidad → criterios → SQL candidatos → RAG por candidato/sección → atributos comparables → ranking estructurado → trade-off`.

Embedding score nunca determina el mejor producto.

### R2 — Need-based recommendation sin target — CRITICAL
Casos construcción, delivery, cámara, simple-use y B2B describen una necesidad sin nombrar modelo. Actualmente caen demasiado en `COMMERCIAL_REASONING/GENERAL_COMMERCIAL` y generan preguntas genéricas.

Cuando exista suficiente situación/problema/prioridad, se debe buscar catálogo y recomendar; no preguntar por obligación Android/iOS, pantalla, tipo de dispositivo, etc.

### R3 — Truth Boundary entre evidencia y beneficio — CRITICAL
No convertir una especificación en una consecuencia absoluta sin soporte. Ejemplos a bloquear: `sin lags`, `dura todo el día`, `mejor rendimiento de noche` solo por MP, `más eficiente` sin evidencia, `menos reparaciones` como hecho.

FAB debe ser: hecho verificado → ventaja razonable → beneficio contextual, con lenguaje calibrado.

### R4 — N+1 Authority / Writer obedience — CRITICAL
`ANSWER_ONLY` debe impedir preguntas generadas. N+1 tiene autoridad sobre el writer.

Antes de preguntar validar relevancia, no repetición, factibilidad de resolver la respuesta, etapa comercial y correlación con tema/producto.

Agregar señal de `pendingCommercialAction`/equivalente para interpretar `sí/dale/ya` por contexto.

### R5 — Buying intent / stock-price-reservation progression — CRITICAL
Distinguir interés, consideración, validación de compra, decisión y transacción.

Ejemplo: producto ya recomendado + precio conocido + `¿ese tiene stock?` → responder disponibilidad y, si el contexto es de compra, ofrecer reserva. Si el cliente ya dijo `si hay lo compro`, no pedir un segundo consentimiento: iniciar flujo transaccional.

### R6 — Reserva 1 unidad — CRITICAL
PURCHASE de 1 unidad sigue yendo a `ASSISTED_HANDOFF` en 3 turnos del run. Debe cumplir contrato:
`producto resuelto → DNI/CE → nombre completo → dirección → SP idempotente → confirmación real`.

2+ unidades mantiene handoff.

### R7 — Institutional retrieval precision — HIGH
La KB ya contiene envío gratis >= S/250, pagos, contraentrega, devoluciones/reembolsos. Cuando el bot afirma no tener el dato, es un fallo de topic/retrieval/ranking, no una ausencia de contenido.

No añadir condiciones inventadas a políticas recuperadas.

### R8 — Institutional/commercial memory separation — HIGH
Preguntas de privacidad, ubicación, garantía, etc. no deben contaminar `useCase`, prioridades o SPIN del producto.

### R9 — Alternative/objection identity consistency — HIGH
En objeciones aparece mezcla de producto objetivo Armor22 con producto_id de X12 Pro. La alternativa debe convertirse en candidato/recomendación explícita sin corromper queryTarget/active/selected.

### R10 — B2B quote progression — HIGH
`QUOTE_DISCOVERY` no debe repetir `¿qué modelo?` si el cliente está dando necesidades de campo/resistencia. Si no eligió modelo, recomendar candidatos del catálogo y después handoff con contexto.

### R11 — Image N+1 — MEDIUM / CONTRACT CHANGE
La imagen debe responder primero la solicitud real. N+1 puede ser contextual (`precio/stock`, comparación, etc.) solo si aporta y el stage lo justifica.

El contrato QA actual de IMAGE exige respuesta URL-only; si se quiere texto + follow-up, debe cambiarse deliberadamente el contrato/payload sin romper la autoridad de URLs. Recomendación: mantener URLs autoritativas como dato estructurado y permitir un `nextBestAction`/mensaje comercial separado según canal.

### R12 — Reliability / persistence — CRITICAL
5/88 turnos no persistieron. G100-20 no aparece en las tablas de sesión/conversación. Antes de certificar, identificar el error exacto del HTTP turn/persistencia y garantizar atomicidad/fail behavior.

### R13 — Oracle correctness — HIGH
Completar correcciones conocidas: alias NBA histórico, evidencia RAG completa, escenarios de reserva y truth-checking. No suavizar el Oracle para ocultar fallos reales.
