## 0. Cómo funciona realmente la memoria/contexto

No se reprocesa toda `ia_conversaciones` en cada turno.

La arquitectura actual usa:

1. `ia_contexto.contexto` como **estado canónico compacto** del session_id: producto activo/seleccionado/recomendado, necesidad, prioridades, presupuesto, etapa, N+1, referencia y trace;
2. `ia_conversaciones` como **histórico/auditoría** y fuente de historia reciente para el planner;
3. `RecentHistoryLlmProvider` entrega al planner solo los últimos 6 mensajes (aprox. 3 turnos completos), además del estado compacto;
4. al terminar el turno se persisten atómicamente conversación + nuevo contexto.

Por tanto, un producto viejo puede permanecer correctamente en `ia_contexto`; el bug aparece si el turno actual no consigue demostrar que el cliente mencionó otro producto y entonces el sistema reutiliza ese producto activo como fallback.

## 1. PRODUCT FOCUS — recomendación Armor 22 pero foco persistido X12 Pro

Estado: **FIXED-CODE / PENDIENTE LIVE**

Evidencia real en `G100-01-CONSTRUCTION`, turno `cual me recomiendas entonces?`:

- respuesta: recomienda **Armor 22**;
- `recommendedProduct = Armor 22`;
- `salientProduct = Armor 22`;
- `lastResolvedProductId = P-ARMOR-22-256G`;
- pero persistía `activeProduct = Armor X12 Pro`;
- persistía `queryTarget = Armor X12 Pro`;
- incluso `producto_objetivo_turno.nombre = Armor X12 Pro` mientras `producto_id = P-ARMOR-22-256G`.

Causa raíz:

`HybridConversationEngine` podía cambiar `quote/recommendedProduct/salientProduct` al ganador de ranking, pero si ya existía `activeProduct`, el foco activo no se alineaba con el nuevo ganador. El siguiente follow-up factual podía volver al producto viejo.

Cambio aplicado en `StateReducer`:

Cuando un turno `RAG_RECOMMENDATION` tiene ganador real y ese ganador coincide con `recommendedProduct`:

1. `activeProduct = winner`;
2. `salientProduct = winner`;
3. `queryTarget = winner`;
4. `activeProductId/Code` se alinean con `lastResolvedProductId/Code`;
5. `selectedProduct` NO cambia: recomendación no equivale a selección del cliente.

## 3. TOP TIE — recomendación por empate

Estado: **OPEN / AHORA OBSERVABLE**

En el primer turno de construcción:

- X12 Pro = 1.0;
- X13 = 1.0;
- Armor 22 = 1.0;
- único criterio efectivo: `RESISTENCIA`.

El sistema eligió X12 Pro por orden, aunque no había diferencia demostrada. Luego, al aparecer `BATERIA`, Armor 22 pasó a ganar claramente.

Esto no es el mismo bug que el foco activo, pero produce sensación de “cambio de producto”. Ahora quedará marcado como `recommendationTopTie=true` / `arbitraryWinnerRisk=true` para corregir la política general sin hardcode.

## 4. G100-20 — `el 22` termina en X13

### LIVE-REF-220811-02
Estado: **FIXED-CODE / PENDIENTE LIVE**

Evidencia exacta de Supabase:

1. `armro x13 cuanto ta` → X13 correcto;
2. `y stk?` → X13 correcto;
3. `foto ps` → X13 correcto;
4. `y el 22 es mejor bateria?` → incorrectamente `ACTIVE_PRODUCT_FALLBACK`, X13, `PRODUCT_OUTSIDE_ALLOWLIST`;
5. `ya el 22 quiero` → incorrectamente inició reserva de X13.

Causa raíz doble:

1. `ReferenceResolver` determinístico corre antes de que existan candidatos SQL del turno. Su universo contenía X13 pero todavía no Armor 22, por lo que `22` no podía resolverse y se reutilizaba X13.
2. `DecisionValidator` permitía que ese fallback viejo sobreescribiera un target canónico del turno actual si `mentionedProducts` venía vacío.
3. `SqlBridgeErpRepository` daba score insuficiente a aliases puramente numéricos (`22`) salvo que también apareciera la familia `Armor`.

Cambios aplicados:

- alias numérico de modelo se recupera solo con señal contextual de producto (`el 22`, `22 cuanto`, `22 stock`, `22 camara`, etc.);
- falla cerrado para fecha, edad y cantidad (`22 equipos`, `22 años`, fechas);
- si SQL devuelve exactamente un candidato nuevo distinto del producto activo, ese candidato tiene autoridad sobre un planner que solo repite el activo viejo;
- un target canónico actual ya no puede ser reemplazado por `ACTIVE_PRODUCT_FALLBACK`;
- compra solo cambia `selectedProduct` cuando la selección es autorizada/unívoca;
- mención de segundo producto crea par de comparación y no compra implícita;
- se añadieron 7 comentarios de autoridad directamente en `DecisionValidator.ts` para mantener trazable el contrato.

Regresión añadida:

`canonical planner target from current SQL candidates beats stale active fallback`.

Próximo Live debe demostrar:

- con X13 activo, `y el 22 es mejor bateria?` debe poner Armor 22 como target del turno y formar X13/22 para comparar cuando corresponda;
- `ya el 22 quiero` debe dejar `selectedProduct=Armor 22`, `activeProduct=Armor 22`, `queryTarget=Armor 22` e iniciar reserva del 22;
- nunca debe reservar X13 por arrastre del contexto si el turno actual resolvió un producto distinto.

## 6. Rol del workflow n8n `stech-backend-events`

Ese workflow NO es memoria ni decide producto/contexto.

Su función actual es ser gateway de eventos posteriores del backend:

- `conversation.turn.completed`;
- `purchase.intent`;
- `handoff.requested`;
- `notification.requested`.

Valida autenticación/contrato, enruta el evento y responde. Sus nodos 04A–04D son hoy puntos de extensión/acuse; no llaman al workflow comercial principal ni reconstruyen `ia_contexto`.

La autoridad conversacional permanece en el backend + Supabase.
